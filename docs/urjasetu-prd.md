# UrjaSetu — Engine PRD

**Version** 1.0
**Audience** An AI coding agent executing this spec, plus 2–3 human reviewers.
**Scope of this document** The simulation engine and agent network only.

---

## 0. How to use this document

This PRD is written to be executed module by module. Every module has:

- an **interface** (exact signatures — do not invent alternatives)
- a **specification** (what the code must do)
- **invariants** (properties that must hold at all times; violations raise, never warn)
- **acceptance checks** (executable tests; a module is not done until all pass)

Rules for the executing agent:

1. Build modules in the order given in §11. Do not start a module until the previous one's acceptance checks pass.
2. If a specification is ambiguous, implement the simplest behaviour that satisfies the invariants, and record the choice in `DECISIONS.md`.
3. Never silently catch an invariant violation. Invariants raise `InvariantError`.
4. Do not add dependencies beyond §2 without recording the reason in `DECISIONS.md`.
5. All randomness goes through a single seeded RNG (§3.4). No module calls `random` or `numpy.random` directly.

---

## 1. Scope

### In scope

- Discrete-event simulation loop over 15-minute settlement blocks
- Seven agent roles (§4)
- Market clearing, constraint checking, flow reshaping, settlement
- Battery custody with shared storage and claims
- Transformer thermal ageing and risk ranking
- LLM integration at three non-blocking call sites
- Event bus, persistence, configuration
- A headless CLI runner that executes N simulated days and emits a run summary

### Explicitly out of scope for this document

- **User interface of any kind.** No web server, no WebSocket, no rendering. The engine exposes an event stream and a database; consuming them is another document's problem.
- **Data acquisition, cleaning, or ingestion.** The engine consumes a pre-built meter feed through the interface in §3.2. How that feed is produced is another document's problem.

The engine must be runnable and testable with a synthetic meter feed generated by the fixtures in §10. No external data source is required to pass any acceptance check in this document.

## 3. Domain model

### 3.1 Core entities

```python
@dataclass(frozen=True)
class House:
    house_id: str
    transformer_id: str
    phase: Literal["A", "B", "C"]
    distance_m: float          # electrical distance from transformer, for voltage calc
    has_pv: bool
    pv_kw: float               # 0.0 if has_pv is False
    has_battery: bool
    battery_kwh: float         # usable capacity, 0.0 if has_battery is False
    battery_max_kw: float      # charge/discharge power limit
    retail_tariff: float       # INR/kWh, the household's DISCOM slab rate

@dataclass(frozen=True)
class Transformer:
    transformer_id: str
    rating_kva: float
    rated_top_oil_rise_c: float
    rated_hotspot_rise_c: float
    rated_life_hours: float
    replacement_cost_inr: float

@dataclass(frozen=True)
class MeterTick:
    block: int
    house_id: str
    load_kwh: float            # gross consumption this block, >= 0
    gen_kwh: float             # gross PV generation this block, >= 0
    ambient_c: float

@dataclass(frozen=True)
class Order:
    order_id: str
    block: int
    house_id: str
    side: Literal["offer", "bid"]
    quantity_kwh: float        # > 0
    limit_price: float         # offer: floor. bid: ceiling.

@dataclass(frozen=True)
class Trade:
    trade_id: str
    block: int
    seller_id: str
    buyer_id: str
    quantity_kwh: float
    clearing_price: float
    curtailed_fraction: float  # 0.0 if untouched by flow agent

@dataclass(frozen=True)
class StorageClaim:
    claim_id: str
    owner_id: str              # who owns the energy
    custodian_id: str          # whose battery holds it
    quantity_kwh: float        # remaining, after round-trip loss
    cost_basis: float          # INR/kWh the owner effectively paid
    opened_block: int
```

### 3.2 Meter feed interface

The engine consumes meter data exclusively through this protocol. Any implementation satisfying it is acceptable.

```python
class MeterFeed(Protocol):
    def houses(self) -> list[House]: ...
    def transformers(self) -> list[Transformer]: ...
    def ticks(self, block: int) -> list[MeterTick]: ...
    def forecast(self, house_id: str, block: int, horizon: int) -> list[MeterTick]: ...
    def total_blocks(self) -> int: ...
```

`forecast` returns the agent's *belief*, not truth. A default implementation may return truth with noise applied via the seeded RNG; a perfect-foresight implementation is acceptable for testing only and must be flagged in the run summary.

### 3.3 Topology

Topology is configuration, not code. The engine must accept any N transformers and M houses without modification. No module may assume N == 1.

### 3.4 Determinism

A single `numpy.random.Generator` is created from `config.seed` at startup and passed explicitly to any component needing randomness.

**Invariant D1.** Two runs with identical config and identical meter feed produce byte-identical `run_summary.json`. Enforced by acceptance check §10.1.

## 4. Agent roles

Agents are logical roles inside one process, not separate services. Each is a class with a `handle(event) -> list[Event]` method subscribing to the event bus (§5.2).

| Role | Count | Owns state across blocks |
|---|---|---|
| `ProsumerAgent` | one per PV house | yes — price memory, battery SoC |
| `ConsumerAgent` | one per house | yes — spend ledger |
| `MarketAgent` | one | no |
| `GridSentinel` | one | no |
| `FlowAgent` | one | no |
| `TransformerHealthAgent` | one | **yes — cumulative loss of life** |
| `SettlementAgent` | one | yes — bill ledger |

`GridSentinel` and `FlowAgent` are separate classes but may live in one module; the sentinel decides *whether* there is a breach, the flow agent decides *what to do about it*. Do not merge their responsibilities.

## 5. Tick pipeline

### 5.1 Sequence

```
for block in range(total_blocks):
    ticks      = feed.ticks(block)
    orders     = collect_orders(ticks, block)         # prosumer + consumer agents
    trades     = market.clear(orders)                 # pass 1
    breach     = sentinel.check(trades, ticks)
    if breach:
        plan   = flow.reshape(trades, ticks, breach)
        trades = market.clear(plan.constrained_orders) # pass 2
        breach = sentinel.check(trades, ticks)
        if breach:
            trades = flow.fallback_curtail(trades, breach)
    ageing     = health.apply(trades, ticks)
    bills      = settlement.settle(trades, ageing)
    persist(block, orders, trades, ageing, bills)
```

### 5.2 Event bus

In-process publish/subscribe. `dict[str, list[Callable]]`. Synchronous dispatch in subscription order. Every event published is also appended to an in-memory ring buffer of the last 500 events, exposed as `engine.recent_events()` for downstream consumers.

Event types, minimum set:
`block_opened`, `order_submitted`, `market_cleared`, `breach_detected`, `reshape_proposed`, `reshape_applied`, `fallback_curtailed`, `ageing_applied`, `block_settled`.

Every event carries `block`, `agent_id`, and a `payload` dict.

### 5.3 Iteration bound

**Invariant P1.** The clear → check → reshape loop executes at most 2 clearing passes per block. After the second failed check, `fallback_curtail` runs unconditionally and its output is final.

### 5.4 Latency

**Invariant P2.** No module in the tick path performs I/O other than SQLite writes. LLM calls happen outside the tick path (§9).

**Invariant P3.** Median tick duration under the reference config (30 houses, 2 transformers) is under 50ms, measured by acceptance check §10.7.

## 6. Module specifications

### 6.1 `agents/prosumer.py`

**Interface**

```python
class ProsumerAgent:
    def __init__(self, house: House, rng, strategy: StrategyParams): ...
    def build_offer(self, block: int, feed: MeterFeed) -> Order | None: ...
    def on_settled(self, block: int, trades: list[Trade], claims: list[StorageClaim]) -> None: ...
    @property
    def battery_soc_kwh(self) -> float: ...
```

**Specification**

Forecast net surplus for `block` as `gen_forecast - load_forecast`, where each forecast is an exponentially weighted moving average over the same block-of-day across the last 7 simulated days, blended with the feed's forecast. Alpha is configurable, default 0.3. On day 1, fall back entirely to the feed forecast.

Reserve price:

```
floor = max(feed_in_tariff, expected_evening_price * strategy.discount)
```

`expected_evening_price` is the agent's own EWMA of clearing prices observed in evening blocks (configurable window, default blocks 68–84). `strategy.discount` is set once per simulated day by the LLM layer (§9) and defaults to 0.85 when the LLM is disabled.

If surplus <= `config.min_order_kwh`, return `None`.

**Invariants**

- **PR1.** `battery_soc_kwh` is always in `[0, house.battery_kwh]`.
- **PR2.** An offer's quantity never exceeds forecast surplus plus available discharge from claims the agent owns.
- **PR3.** `build_offer` is pure with respect to agent state; state mutates only in `on_settled`.

**Acceptance checks**

- Given a constant feed for 10 days, offers converge to a stable price (variance across the last 3 days below 2% of mean).
- Given zero generation, `build_offer` returns `None` for every block.
- PR1 holds across a 30-day run with randomised charge/discharge.

### 6.2 `agents/consumer.py`

**Interface**

```python
class ConsumerAgent:
    def __init__(self, house: House, rng, strategy: StrategyParams): ...
    def build_bid(self, block: int, feed: MeterFeed) -> Order | None: ...
    def on_settled(self, block: int, trades: list[Trade], baseline_cost: float) -> None: ...
    @property
    def cumulative_spend(self) -> float: ...
    @property
    def cumulative_baseline(self) -> float: ...
```

**Specification**

Forecast deficit as `load_forecast - gen_forecast`, floored at zero. Bid ceiling:

```
ceiling = house.retail_tariff * (1 - strategy.margin)
```

`strategy.margin` defaults to 0.05.

`baseline_cost` passed to `on_settled` is what this household would have paid the DISCOM for the same consumption in the same block. The agent accumulates both its actual spend and this baseline.

**Invariants**

- **CN1 (hard cap, enforced).** `order.limit_price <= house.retail_tariff` for every bid. Violation raises at construction.
- **CN2 (monthly guarantee, asserted).** At the end of every block, `cumulative_spend <= cumulative_baseline`. Violation raises `InvariantError`.

CN2 is implied by CN1 and should never fire. It exists as a continuously checked assertion, not as a fallback mechanism. If it ever fires, there is a bug in settlement, not in bidding.

**Acceptance checks**

- Attempting to construct a bid above retail tariff raises.
- Over a 30-day run with 30 houses, CN2 never fires.
- With P2P disabled (`config.p2p_enabled = False`), `cumulative_spend == cumulative_baseline` exactly.

### 6.3 `market/clearing.py`

**Interface**

```python
def clear(orders: list[Order]) -> ClearingResult: ...

@dataclass(frozen=True)
class ClearingResult:
    trades: list[Trade]
    clearing_price: float | None
    unmatched_offers: list[Order]
    unmatched_bids: list[Order]
```

**Specification**

Uniform-price double auction.

1. Sort offers ascending by `limit_price`, bids descending by `limit_price`.
2. Walk both lists, matching while `bid.limit_price >= offer.limit_price`.
3. `clearing_price` is the midpoint of the last matched pair's limit prices.
4. Every matched trade settles at `clearing_price`, not at its own limit.
5. Partial fills are permitted; split the larger order and carry the remainder forward within the same block.
6. Ties on price break by order_id ascending, for determinism.

If no pair matches, return an empty result with `clearing_price = None`.

**Invariants**

- **MK1.** `sum(trade.quantity for trades) <= min(total_offered, total_bid)`.
- **MK2.** For every trade: `seller.limit_price <= clearing_price <= buyer.limit_price`.
- **MK3.** Clearing is deterministic: identical order lists produce identical trade lists including trade_ids.

**Acceptance checks**

- Hand-built book of 5 offers and 5 bids produces the analytically correct clearing price.
- Empty book returns empty result without raising.
- Shuffling input order does not change output (after tie-break sorting).
- MK2 holds across a 30-day run.

### 6.4 `grid/sentinel.py`

**Interface**

```python
class GridSentinel:
    def check(self, trades: list[Trade], ticks: list[MeterTick]) -> Breach | None: ...

@dataclass(frozen=True)
class Breach:
    transformer_id: str
    kind: Literal["loading", "phase", "voltage"]
    severity: float            # 1.0 == exactly at limit
    detail: dict
```

**Specification**

Compute net power per house from `ticks` adjusted by cleared trades, then evaluate three checks per transformer. Return the highest-severity breach, or `None`.

**Loading.**
```
K = sum(abs(net_kw_h) for h in houses_on_transformer) / transformer.rating_kva
breach if K > config.loading_limit          # default 1.0
```

**Phase imbalance.**
```
imbalance = max(P_A, P_B, P_C) / mean(P_A, P_B, P_C)
breach if imbalance > config.phase_limit    # default 1.15
```

**Voltage.** Linearised LinDistFlow. Do not implement a full power flow.
```
dV_i = sum over path(transformer -> i) of (R_seg * P_seg + X_seg * Q_seg) / V_nom
breach if abs(dV_i / V_nom) > config.voltage_band   # default 0.06
```
Segment impedances derive from `house.distance_m` and configured per-metre R and X. Reactive power Q may be approximated from a configured power factor.

**Invariants**

- **SN1.** `check` is pure. It never mutates trades, ticks, or agent state.
- **SN2.** `severity >= 1.0` for any returned breach, and `None` implies all three checks are within limits.

**Acceptance checks**

- A hand-built case at exactly 100% loading returns `None`; at 100.1% returns a loading breach.
- A perfectly balanced three-phase case never returns a phase breach regardless of magnitude.
- Voltage deviation for a single-house radial feeder matches a hand-computed value to within 1%.

### 6.5 `grid/flow.py`

**Interface**

```python
class FlowAgent:
    def reshape(self, trades: list[Trade], ticks: list[MeterTick],
                breach: Breach, batteries: BatteryBook) -> ReshapePlan: ...
    def fallback_curtail(self, trades: list[Trade], breach: Breach) -> list[Trade]: ...

@dataclass(frozen=True)
class ReshapePlan:
    constrained_orders: list[Order]
    battery_charges: dict[str, float]   # house_id -> kWh to absorb this block
    new_claims: list[StorageClaim]
    feasible: bool
    objective_value: float
```

**Specification**

Formulate and solve a linear program with `scipy.optimize.linprog`.

**Decision variables**
- `c_t ∈ [0, 1]` for each trade `t` — fraction retained (1.0 means untouched)
- `b_h >= 0` for each house with a battery — kWh absorbed this block

**Objective**

Maximise `Σ_t (c_t · quantity_t · clearing_price) − Σ_h (b_h · storage_fee)`

**Constraints**
- Transformer loading: `Σ net_kw(c, b) <= rating · loading_limit` per transformer
- Phase: per-phase net within `phase_limit` of the mean
- Voltage: linearised `|dV_i| <= voltage_band` per house
- Battery power: `b_h <= house.battery_max_kw · 0.25`
- Battery capacity: `b_h <= house.battery_kwh − soc_h`
- Retention: `c_t <= 1.0`

**Battery custody.** Every kWh absorbed into house H's battery on behalf of house O creates a `StorageClaim` with `owner_id = O`, `custodian_id = H`.

- Round-trip efficiency `config.round_trip_efficiency` (default 0.90) is deducted from the claim at creation: a 4.1 kWh absorption creates a 3.69 kWh claim.
- The custodian is paid `config.storage_fee_inr_per_kwh` (default 0.35) per kWh absorbed, flat, not negotiated.
- `cost_basis` on the claim is the clearing price at which the energy would otherwise have sold, plus the storage fee, divided by the retained efficiency. This is the number the owner's agent must beat when deciding to discharge later.
- On discharge, claims are consumed **owner-first**: a custodian may not discharge its own energy while holding an unexpired claim, unless the claim owner has declined at the current price. Ties break by `opened_block` ascending (oldest claim first).

**Fallback.** If the LP is infeasible, `fallback_curtail` applies a uniform retention fraction to all trades on the breaching transformer, computed as the ratio needed to bring loading to exactly `loading_limit`. This always succeeds.

**Invariants**

- **FL1.** After a successful reshape, `sentinel.check` on the re-cleared result returns `None`, or the fallback path runs.
- **FL2.** `Σ new_claims.quantity <= Σ battery_charges · round_trip_efficiency`.
- **FL3.** No claim's `custodian_id` refers to a house without a battery.
- **FL4.** Total energy is conserved: generation equals consumption plus net battery change plus losses, per block, to within 1e-6 kWh.

**Acceptance checks**

- A constructed 112%-loading case reshapes to <= 100% in one pass.
- With all batteries full, the LP still returns a feasible curtail-only plan.
- With batteries disabled in config, behaviour is identical to curtailment-only.
- FL4 holds across a 30-day run.
- Deliberately infeasible constraints trigger `fallback_curtail` and never raise.

### 6.6 `grid/health.py`

**Interface**

```python
class TransformerHealthAgent:
    def apply(self, trades: list[Trade], ticks: list[MeterTick]) -> AgeingResult: ...
    def ageing_adder(self, transformer_id: str) -> float: ...   # INR/kWh
    def risk_rank(self) -> list[tuple[str, float]]: ...
    def save(self, path: str) -> None: ...
    def load(self, path: str) -> None: ...
```

**Specification — thermal model**

IEEE C57.91. All algebraic; no iteration.

```
K          = load_kva / rating_kva
dTO        = rated_top_oil_rise * ((K**2 * R + 1) / (R + 1)) ** n
theta_h    = ambient_c + dTO + rated_hotspot_rise * K ** (2 * m)
F_AA       = exp(15000 / 383 - 15000 / (theta_h + 273))
loss_hours = F_AA * 0.25
```

Defaults: `R = 5.0`, `n = 0.8`, `m = 0.8` for ONAN distribution units. All configurable.

**Specification — ageing adder**

```
marginal_loss = loss_hours(with_trades) - loss_hours(without_trades)
adder = (marginal_loss / rated_life_hours) * replacement_cost / block_kwh
```

Clamp to `[0, config.max_ageing_adder]` (default 2.00 INR/kWh). The adder computed in block `t` is applied to clearing in block `t+1`, never retroactively.

**Specification — risk ranking**

LightGBM classifier over per-transformer features: rolling mean and max of K, rolling mean and max of hot-spot temperature, cumulative loss of life fraction, count of voltage-band excursions in the trailing window, ambient temperature percentile. Target during development is a synthetic label derived from cumulative loss of life crossing a threshold. Expose `feature_importances_` so downstream consumers can explain a ranking.

The model must be optional: with `config.lightgbm_enabled = False`, `risk_rank` falls back to sorting by cumulative loss of life.

**Invariants**

- **HL1.** Cumulative loss of life is monotonically non-decreasing per transformer.
- **HL2.** `ageing_adder` is in `[0, max_ageing_adder]` and never `NaN`.
- **HL3.** State survives a `save`/`load` round trip exactly (§10.5).
- **HL4.** The adder applied in block `t` was computed no later than block `t-1`.

**Acceptance checks**

- At rated load and rated ambient, `F_AA` equals 1.0 to within 1e-3.
- A 10°C rise in hot-spot temperature roughly triples `F_AA` (within 10% of the Arrhenius prediction).
- 30 days at 50% load consumes less life than 30 days at 90% load.
- `save`/`load` round trip produces identical `risk_rank` output.

### 6.7 `settlement/settle.py`

**Interface**

```python
class SettlementAgent:
    def settle(self, trades: list[Trade], ageing: AgeingResult) -> list[BillLine]: ...

@dataclass(frozen=True)
class BillLine:
    block: int
    house_id: str
    counterparty_id: str
    quantity_kwh: float
    energy_inr: float
    transaction_inr: float
    wheeling_inr: float
    cross_subsidy_inr: float
    storage_fee_inr: float
    ageing_inr: float
    net_inr: float             # positive = house pays
```

**Specification**

Per trade, itemised, never aggregated at source:

```
energy          = qty * clearing_price
transaction     = qty * config.transaction_charge / 2      # each side, default 0.42 total
wheeling        = qty * config.wheeling_charge             # buyer only, default 1.01
cross_subsidy   = qty * config.cross_subsidy if config.cross_subsidy_enabled else 0
storage_fee     = per §6.5, payable by claim owner to custodian
ageing          = qty * health.ageing_adder(transformer_id)
```

Charges are configuration values, not literals in code.

**Invariants**

- **ST1.** `Σ net_inr` across all parties in a block equals the total of non-energy charges collected (the DISCOM's take plus custodian fees). Money is conserved; check to within 1e-6.
- **ST2.** Every `BillLine` has `energy_inr + transaction_inr + wheeling_inr + cross_subsidy_inr + storage_fee_inr + ageing_inr == net_inr` to within 1e-9.
- **ST3.** No bill line exists without a corresponding trade or claim.

**Acceptance checks**

- A single hand-computed trade produces exactly the expected six components.
- ST1 holds across a 30-day run.
- Toggling `cross_subsidy_enabled` changes only the `cross_subsidy_inr` column.

### 6.8 `sim/baseline.py`

**Specification**

A parallel accounting path simulating the same meter feed under net metering, with no trading:

- Surplus is exported and credited 1:1 against consumption
- Credits carry forward up to `config.credit_carryforward_blocks` (default 12 months) then lapse
- No wheeling or transaction charges apply
- Transformer loading is computed from raw net export with no reshaping, so breaches are recorded but never acted on

This module produces the counterfactual numbers used by `ConsumerAgent.cumulative_baseline` and by the run summary. It shares the thermal model in §6.6 so that loss-of-life comparison is apples to apples.

**Invariants**

- **BL1.** Baseline and P2P runs consume the identical meter feed and identical seed.
- **BL2.** Baseline never modifies any agent state.

**Acceptance checks**

- With `p2p_enabled = False`, the main engine's bills equal the baseline's bills exactly.
- Baseline transformer loss of life is >= P2P loss of life over a 30-day run under the reference config. If this fails, the ageing price signal is not working and is a blocking bug.

## 7. Persistence

SQLite, single file, five tables:

| Table | Written per | Survives restart |
|---|---|---|
| `meter_tick` | block | pre-computed, read-only |
| `order_book` | block | no (truncate on new run) |
| `trade` | block | no |
| `bill_line` | block | no |
| `transformer_state` | block | **yes** |

`transformer_state` is the only table the engine reads back on startup. It carries cumulative loss of life, and losing it destroys the memory story. Write it every block, not at shutdown.

**Invariant PS1.** After a hard kill and restart mid-run, cumulative loss of life resumes from the last persisted block with no gap and no double-count.

## 9. LLM layer

Three call sites. All outside the tick path. All optional.

| Site | Frequency | Input | Output | On failure |
|---|---|---|---|---|
| Daily strategy | once per simulated day per agent | weather outlook, own 7-day price history | `StrategyParams{discount, margin}` | keep previous params |
| Breach diagnosis | on `breach_detected` | breach object, transformer state | one plain-language line | emit a templated line |
| Operator query | on demand | question, persisted block history | plain-language answer | return "unavailable" |

**Constraints**

- **LM1.** The LLM may set only `StrategyParams.discount` and `StrategyParams.margin`. It may not alter orders, trades, constraints, clearing, or settlement. Returned values are clamped to configured ranges before use.
- **LM2.** Every LLM call runs with a timeout. On timeout the fallback in the table applies. The tick loop never blocks.
- **LM3.** With `llm_enabled = False`, the engine produces a complete, valid run using defaults. All acceptance checks in this document must pass with the LLM disabled.

**Acceptance checks**

- A mocked LLM returning out-of-range values results in clamped, in-range params.
- A mocked LLM that always times out produces a run identical to `llm_enabled = False`.

## 10. Integration acceptance checks

These run against the whole engine. All must pass for the engine to be considered done.

1. **Determinism.** Two runs, same config, same feed → byte-identical `run_summary.json`.
2. **Energy conservation.** Across a 30-day run, generation = consumption + net battery change + losses, within 1e-6 kWh per block.
3. **Money conservation.** Invariant ST1 holds in every block of a 30-day run.
4. **Consumer protection.** Invariant CN2 never fires across a 30-day run with 30 houses.
5. **Persistence.** Kill the process at block 500 of 2880, restart, complete the run. Cumulative loss of life matches an uninterrupted run within 1e-9.
6. **Breach resolution.** Inject a transformer derate to 60% at a known block. The engine resolves within the 2-pass bound in 100% of injected cases; fallback fires at most once per injection.
7. **Latency.** Median tick under 50ms, 99th percentile under 200ms, reference config.
8. **Baseline comparison.** Baseline loss of life >= P2P loss of life over 30 days.
9. **Topology independence.** Full run passes with `n_transformers` set to 1, 2, and 4 without code changes.
10. **LLM-off parity.** Full suite passes with `llm_enabled = False`.

A `run_summary.json` is emitted at the end of every run containing, at minimum: total traded kWh, mean clearing price, count of breaches by kind, count of reshapes and fallbacks, cumulative loss of life per transformer, total DISCOM charge revenue, and the same figures for the baseline path.

## 11. Build order

Each stage ends with a checkpoint. Do not proceed past a failing checkpoint.

| Stage | Modules | Checkpoint |
|---|---|---|
| 1 | config, domain model, event bus, seeded RNG, synthetic feed fixture | A 1-day run emits `block_opened` and `block_settled` for every block |
| 2 | `market/clearing.py` | §6.3 acceptance checks pass |
| 3 | `agents/prosumer.py`, `agents/consumer.py` | §6.1, §6.2 checks pass; a 7-day run clears trades every day |
| 4 | `settlement/settle.py`, persistence | §6.7 checks and integration check 3 pass |
| 5 | `sim/baseline.py` | Integration check 4 passes; `p2p_enabled=False` parity holds |
| 6 | `grid/sentinel.py` | §6.4 checks pass; breaches are detected and logged but not acted on |
| 7 | `grid/flow.py` — curtailment only | Integration check 6 passes with batteries disabled |
| 8 | `grid/flow.py` — batteries and claims | §6.5 checks pass; integration checks 2 and 6 pass with batteries on |
| 9 | `grid/health.py` — thermal model and adder | §6.6 checks and integration check 8 pass |
| 10 | `grid/health.py` — LightGBM ranking | `risk_rank` returns a stable ordering; falls back cleanly when disabled |
| 11 | LLM layer | §9 checks and integration check 10 pass |
| 12 | Full integration suite | All of §10 passes |

**Stages 1–7 constitute a demonstrable system.** If time runs short, stop at the last passing checkpoint and ship that. A system that passes stage 7 and runs reliably is worth more than one that reaches stage 11 and crashes.

## 12. Failure handling

| Failure | Response |
|---|---|
| LP infeasible | `fallback_curtail`, log `fallback_curtailed`, continue |
| Sentinel breach after 2 passes | `fallback_curtail`, continue |
| LLM timeout or malformed output | Use previous or default params, continue |
| SQLite write failure | Retry once, then raise — do not continue with unpersisted state |
| Invariant violation | Raise `InvariantError` immediately; never catch and continue |
| Meter feed gap | Raise at startup during feed validation, not mid-run |

The engine validates the entire meter feed before block 0. A run that starts must be able to finish.

## 13. Definition of done

- All §10 integration checks pass
- A 30-day run with the default config completes in under 3 minutes wall clock
- `run_summary.json` contains every field listed in §10
- The engine runs to completion with `llm_enabled = False` and `lightgbm_enabled = False`
- `DECISIONS.md` records every ambiguity resolved during implementation
- No module imports anything from a UI or data-ingestion package

## Appendix A — Locked decisions

| Decision | Choice | Rationale |
|---|---|---|
| Agent hosting | Logical roles, one process | 2–3 person team; separate services add ops cost with no demo value |
| Flow levers | Curtailment + batteries | Curtailment guarantees feasibility; batteries preserve value |
| Battery custody | Shared, flat storage fee | Ownership tracked via claims; flat fee avoids a negotiation subsystem |
| Topology | Parameterised N | Ageing price signal needs somewhere to route toward |
| LLM authority | Explanation + daily strategy params only | Keeps the tick path deterministic and fast |
| Consumer protection | Per-block cap enforced, monthly asserted | Cap implies the guarantee; the assertion catches settlement bugs |
| Deferrable loads | Out of scope | Adds a trace line but no visible outcome change |
| Phase steering | Constraint only, not an optimisation lever | Detected and respected; not actively steered in v1 |
| Blockchain settlement | Out of scope | Adds no observable property the ledger lacks |
| RL / MARL policies | Out of scope | Undertrained policies demo worse than tuned heuristics |
